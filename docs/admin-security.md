# אבטחת פאנל הניהול — מסקנות ותוכנית עבודה

> מסמך זה מסכם את ההחלטות והמסקנות מהדיון על אבטחת פעולות האדמין.
> נכתב 2026-06-04. **מומש 2026-06-04** — ראו "סטטוס מימוש" בתחתית.

## סטטוס מימוש (מה כבר עובד)

✅ **כל התוכנית מומשה.** המודל הסופי בשרת:

1. **Gate חיצוני — מפתח גישה סודי (gateKey).** בלי המפתח הנכון אף endpoint של
   אדמין לא עונה, וה-`/admin` בכלל לא נטען. נשמר רק כ-hash בשרת.
2. **שכבת IP allowlist.** ה-`/admin` נטען רק מכתובות IP מאושרות.
3. **התחברות (2 גורמים):** סיסמת Firebase → גורם שני (Passkey/Face ID, או קוד
   מייל כגיבוי) → `adminToken` ל-12 שעות.
4. **קריאת נתונים** (`list-*`, `*-report`, `get-*`) דורשת `verifyAdmin2FA`:
   gateKey + idToken + adminToken.
5. **כל פעולת שינוי** (`set-*`, `create-*`, `delete-*`, `grant-*`, `approve/revoke`,
   פרסום עדכון וכו') דורשת `verifyAdminStepUp` — כלומר את כל מה שב-(4) **ועוד**
   **step-up token טרי**: token ל-2 דקות שנוצר **רק** מחתימת Passkey חיה
   (Face ID / Touch ID / Windows Hello) על אחד המכשירים הרשומים.

המשמעות: גם אם תוקף השיג איכשהו את ה-`adminToken` החי (או פרץ ל-login), הוא לא
יכול **לשנות** כלום בלי חתימה ביומטרית טרייה מהמכשיר הפיזי של דניאל. כל פעולה
"חתומה" בהוכחת נוכחות אמיתית — בדיוק הדרישה המרכזית.

ה-step-up token הוא HMAC HS256 (`use:'admin-stepup'`, 2 דק'), נחתם באותו סוד
שרת. תקף שוב לחלון של 2 דקות כדי ששמירה אחת שמתפצלת לשתי קריאות (למשל מחיר +
סנכרון PayPal) לא תבקש פעמיים — אחר כך פג ופעולה הבאה מבקשת חתימה חדשה.

> הערה: גם `api/admin/draft-release.ts` (קובץ נפרד) מאמת את אותם שלושת הגורמים +
> step-up, עם אותה קריפטוגרפיה בדיוק. אם משנים את פורמט ה-token ב-`paypal.ts`,
> צריך לעדכן גם שם. הרשימה הקנונית של פעולות-שינוי בצד הלקוח: `STEPUP_ACTIONS`
> ב-`src/lib/adminApi.ts`.

## הדרישה המרכזית של דניאל (המטרה)

**כל פעולת אדמין צריכה לעבור אימות מחדש שמוודא שזה האדמין האמיתי — לא רק בדיקה
חד-פעמית בהתחברות.** ההגנה לא צריכה להיות נטו על ההתחברות לחשבון, אלא step-up
auth לכל פעולה רגישה. כך שגם אם מישהו פרץ לחשבון (השיג מייל+סיסמה), הוא עדיין
לא יכול לבצע פעולות אדמין.

## מסקנות אבטחה (העובדות כפי שהן היום)

1. **הגבול האמיתי הוא השרת, לא הלקוח.**
   גם הפאנל באתר וגם זה בתוכנה (Electron) קוראים לאותם endpoints ב-`api/paypal.ts`.
   האבטחה היחידה שקובעת היא הבדיקה בשרת מול `ADMIN_EMAILS`. הסרת UI מהלקוח לבדה
   לא מוסיפה אבטחה — ה-endpoints נשארים פתוחים.

2. **שני רמות gating קיימות היום בשרת:**
   - `verifyAdmin2FA` (idToken של Firebase **+** קוד מייל / adminToken) — לפעולות
     הרגישות: ניהול משתמשים, מפתחות, trials, usage stats, app config, feedback.
   - `verifyAdminEmail` (idToken **בלבד**, בלי קוד מייל) — לפעולות:
     `admin-revenue-report`, `admin-get-ip-allowlist`, **`admin-set-ip-allowlist`**,
     `admin-list-referrals` + שאר ה-referrals, `admin-list-receipts`, `admin-2fa-request`.
   - ⚠️ במיוחד `admin-set-ip-allowlist` מוגן רק ב-idToken — זו שליטה רגישה שצריכה
     לעלות ל-2FA מלא.

3. **חתימת המחשב (`deviceId`) לא מגנה על פעולות האדמין.**
   - היא נבדקת רק לנעילת חשבון למכשיר ולמניעת ניצול trials — **לא** בשום endpoint של אדמין.
   - היא מחושבת בצד הלקוח ונשלחת כטקסט → **ניתנת לזיוף**. ההערה בקוד עצמו
     (`api/start-trial.ts`) מודה: "the deviceId still comes from the client...
     could modify the Electron build to send a fake deviceId".

4. **idToken ניתן לייצור מכל מקום.**
   מי שמשיג מייל+סיסמה של חשבון אדמין יכול לייצר idToken תקין דרך ה-API הציבורי של
   Firebase מכל מחשב — בלי המכשיר המקורי. לכן ה-endpoints שמוגנים רק ב-idToken
   חשופים למי שפרץ את ה-login.

5. **המסקנה:** דווקא קוד המייל (2FA) באתר הוא כרגע הגורם השני האמיתי שנבדק בשרת.
   חתימת המחשב בתוכנה לא נותנת הגנה שרתית.

## הכיוון המומלץ

**פאנל ניהול באתר בלבד + WebAuthn / Passkey כגורם שני אמיתי.**

- Passkey = זוג מפתחות שהמפתח הפרטי שלו לעולם לא עוזב את המכשיר
  (Secure Enclave במק / Windows Hello / Passkey). השרת שומר את המפתח הציבורי ודורש
  שכל פעולה תהיה חתומה.
- יתרונות: עמיד לפישינג, **נבדק בשרת** (לא ניתן לזיוף), זמין גם בדפדפן.
- זה נותן בדיוק את ה"חתימת מכשיר" שדניאל אוהב — אבל עשוי נכון.
- אפשר לדרוש step-up (אימות Passkey טרי) **לכל פעולה רגישה**, מה שמגשים את הדרישה
  המרכזית — לא רק בהתחברות.

## תוכנית עבודה (בוצעה ✅)

1. ✅ **חיזוק מיידי:** כל ה-endpoints שהיו מוגנים רק ב-idToken הועלו ל-`verifyAdmin2FA`
   המלא (כולל `admin-set-ip-allowlist`, revenue, referrals, receipts, sync-plans,
   send-test-email, test-sumit, send-marketing-email, grant-pro, migrate-email).
2. ✅ **step-up per-action:** כל פעולת שינוי דורשת `verifyAdminStepUp` — חתימת
   Passkey טרייה (token ל-2 דק'). מומש כ-`admin-stepup-options` + `admin-stepup-verify`.
3. ✅ **Passkey/WebAuthn לאתר:** רישום + התחברות + step-up, כולם מאומתים בשרת.
4. ✅ **web-only:** פאנל הניהול הוסר מהתוכנה (Electron); נשאר רק קיצור סודי
   (Ctrl+Shift+1) לפתיחת לוגים עם סיסמה.

### דברים שכדאי לזכור להמשך

- **ניהול ה-IP allowlist וה-gateKey** היו פעם מנוהלים מהתוכנה. עכשיו ה-endpoints
  (`admin-set-ip-allowlist`, `admin-set-gate-key`) מוגנים ב-step-up מלא, אבל עדיין
  **אין להם UI באתר**. אם תרצה לשנות IP/מפתח — צריך להוסיף UI בטאב ההגדרות, או
  לערוך ישירות ב-Firestore (`adminSecurity/config`).
- **שחזור גישה אם אבד Passkey:** מתחברים עם קוד מייל (גיבוי) → נכנסים → רושמים
  Passkey חדש בטאב ההגדרות (הרישום דורש רק 2FA, לא step-up — כדי לא להיתקע).

## אילוצים שצריך לזכור

- **Vercel Hobby:** תקרה של 12 פונקציות — אסור להוסיף קבצי `api/` חדשים. רק
  action cases חדשים בתוך `api/paypal.ts` הקיים.
- כבר קיימת שכבת **IP allowlist** ל-`/admin` (אתר + תוכנה).
- מסמכים רגישים בצד הלקוח: לא להוסיף writes ישירים ל-Firestore מה-renderer של התוכנה
  לקולקשנים רגישים — לבנות endpoint ב-Vercel ולקרוא לו עם Firebase idToken.
